# Внедрение сервиса отчётов ТО на российском сервере

## 1. Цель

Перенести сервис ТО с текущей платформы Cloudflare на сервер, физически
расположенный в России, сохранив:

- мобильную форму и локальные черновики;
- загрузку и съёмку фотографий с телефона;
- формирование акта и фотоотчёта в PDF и DOCX;
- создание общего ZIP-архива;
- скачивание ZIP на устройство;
- отправку ZIP на `info@riklab.ru`;
- текущую авторизацию.

## 2. Текущая архитектура

Клиентская часть написана на TypeScript, React и Next.js. Сборка выполняется
через Vinext и сейчас запускается как Cloudflare Worker.

На телефоне хранятся:

- поля формы и чек-лист — в `localStorage`;
- фотографии — в `IndexedDB`.

На сервере временно хранятся:

- печать и подпись руководителя;
- промежуточные PDF и DOCX;
- части комплекта перед сборкой ZIP.

Обычная база данных сейчас не используется. Cloudflare D1 не подключена.

## 3. Рекомендуемая архитектура после переноса

```text
Телефон инженера
        |
      HTTPS
        |
Nginx на российском VPS
        |
Node.js-приложение
   |            |
файловое      SMTP
хранилище     mail.hosting.reg.ru
```

Для первого внедрения рекомендуется один VPS и локальное файловое хранилище.
S3-совместимое хранилище или база данных понадобятся только при дальнейшем
масштабировании и создании централизованного архива отчётов.

## 4. Требования к серверу

Минимальная конфигурация для пилотной эксплуатации:

- Linux x86-64;
- 2 виртуальных процессора;
- 4 ГБ оперативной памяти;
- от 30 ГБ SSD;
- Node.js версии не ниже 22.13;
- Nginx;
- Git;
- systemd или Docker Compose;
- доменное имя и TLS-сертификат.

Если на сервере планируется постоянно хранить готовые отчёты, объём диска
необходимо рассчитывать отдельно. В текущей схеме файлы считаются временными.

## 5. Обязательная адаптация проекта

Текущий серверный код использует API Cloudflare и без изменений на обычном
Node.js-сервере не запустится.

Перед переносом необходимо выполнить следующие изменения.

### 5.1. Серверный запуск

Создать Node.js-точку входа, которая обслуживает клиентское приложение и
существующие API-маршруты:

- `/api/auth/login`;
- `/api/auth/logout`;
- `/api/oven-act/pdf`;
- `/api/oven-act/docx`;
- `/api/oven-report/pdf`;
- `/api/oven-report/docx`;
- `/api/oven-package/part`;
- `/api/oven-package/finalize`.

Форматы запросов и ответов необходимо сохранить, чтобы мобильную часть не
пришлось переписывать.

### 5.2. Файловое хранилище

Вызовы Cloudflare R2 `get`, `head`, `put` и `delete` заменить адаптером
локального файлового хранилища.

Рекомендуемая структура:

```text
/var/lib/riklab-service/
├── permanent/
│   └── director-stamp-signature.png
└── temporary/
    └── oven-packages/
```

Требования:

- приложение имеет права только на этот каталог;
- временные каталоги создаются по случайному идентификатору комплекта;
- запрещается использовать имя файла из запроса как готовый путь;
- временные комплекты старше 24 часов удаляются автоматически;
- печать и подпись не должны находиться в публичном каталоге сайта.

Для нескольких серверов вместо локального диска следует использовать
S3-совместимое хранилище российского провайдера.

### 5.3. Отправка почты

Модуль `cloudflare:sockets` заменить стандартным SMTP-клиентом Node.js,
например Nodemailer.

Параметры:

```dotenv
SMTP_HOST=mail.hosting.reg.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=...
SMTP_PASSWORD=...
MAIL_FROM=...
MAIL_TO=info@riklab.ru
```

ZIP следует передавать в SMTP потоком, не загружая целиком в оперативную
память.

### 5.4. Статические файлы

Обращения через `env.ASSETS` заменить чтением файлов из `public` либо раздачей
статических ресурсов средствами Next.js/Nginx.

Особенно нужны:

- `oven-act-template.pdf`;
- `rik-logo.png`;
- `fonts/DejaVuSans.ttf`;
- `favicon.ico`.

### 5.5. Неиспользуемые компоненты

Cloudflare D1 сейчас не используется и при первом внедрении не требуется.
Cloudflare Images также не является обязательной частью формирования актов и
отчётов.

## 6. Переменные окружения

В production должны быть настроены:

```dotenv
NODE_ENV=production
PORT=3000
PUBLIC_BASE_URL=https://service.riklab.ru

APP_AUTH_LOGIN=...
APP_AUTH_PASSWORD=...
APP_AUTH_SECRET=...

SMTP_HOST=mail.hosting.reg.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=...
SMTP_PASSWORD=...
MAIL_FROM=...
MAIL_TO=info@riklab.ru

STORAGE_DIR=/var/lib/riklab-service
TEMP_FILE_TTL_HOURS=24
```

`APP_AUTH_SECRET` должен быть случайной строкой длиной не менее 32 байт.
Пароли запрещено добавлять в Git, Dockerfile, исходный код или журналы.

Перед production-запуском необходимо сменить пароль сайта и пароль почтового
ящика, которые использовались во время разработки.

## 7. Подготовка сервера

Пример каталогов:

```bash
sudo mkdir -p /opt/riklab/service-to-reports
sudo mkdir -p /var/lib/riklab-service/permanent
sudo mkdir -p /var/lib/riklab-service/temporary/oven-packages
sudo useradd --system --home /opt/riklab --shell /usr/sbin/nologin riklab
sudo chown -R riklab:riklab /opt/riklab /var/lib/riklab-service
sudo chmod 750 /var/lib/riklab-service
```

Печать и подпись:

```text
/var/lib/riklab-service/permanent/director-stamp-signature.png
```

Файл должен читаться пользователем `riklab` и не должен открываться по URL.

## 8. Сборка и запуск

После реализации Node.js-адаптера в проект необходимо добавить отдельные
production-команды, например:

```json
{
  "scripts": {
    "build:node": "...",
    "start:node": "..."
  }
}
```

После этого стандартная последовательность развёртывания:

```bash
cd /opt/riklab/service-to-reports
git pull --ff-only
npm ci
npm run build:node
sudo systemctl restart riklab-service
```

До появления `build:node` и `start:node` эти команды использовать нельзя:
текущая команда `vinext start` рассчитана на Cloudflare-окружение.

Сервис systemd должен:

- запускаться от пользователя `riklab`;
- читать секреты из отдельного файла окружения;
- автоматически перезапускаться после сбоя;
- иметь доступ на запись только к `STORAGE_DIR`;
- принимать соединения только на локальном порту, например `127.0.0.1:3000`.

## 9. Nginx и HTTPS

Nginx принимает внешние HTTPS-запросы и передаёт их приложению.

Обязательные настройки:

- перенаправление HTTP на HTTPS;
- TLS-сертификат;
- максимальный размер запроса не менее 40 МБ;
- увеличенный тайм-аут формирования отчёта;
- запрет доступа к служебным каталогам и `.env`;
- передача исходного протокола и IP-адреса приложению.

Рекомендуемые значения:

```nginx
client_max_body_size 40m;
proxy_connect_timeout 30s;
proxy_send_timeout 300s;
proxy_read_timeout 300s;
```

Приложение должно оставаться доступным только через HTTPS. Без HTTPS камера,
cookie авторизации и часть функций iPhone могут работать некорректно.

## 10. Очистка и резервное копирование

Каждый час необходимо удалять временные комплекты старше 24 часов.

Резервному копированию подлежат:

- файл печати и подписи;
- production-конфигурация;
- секреты — в отдельном защищённом хранилище;
- исходный код уже хранится в GitHub.

Временные PDF, DOCX и ZIP резервировать не нужно.

Если позже появится централизованный архив отчётов, для него потребуется
отдельная политика хранения и резервного копирования.

## 11. Проверка перед запуском

### Функциональная проверка

1. Вход и выход из системы.
2. Выбор объекта, печи, положения печи и инженера.
3. Сохранение черновика после закрытия браузера.
4. Съёмка и загрузка фотографий с iPhone и Android.
5. Автоматическая оптимизация старых фотографий.
6. Формирование четырёх файлов:
   - акт PDF;
   - акт DOCX;
   - фотоотчёт PDF;
   - фотоотчёт DOCX.
7. Скачивание ZIP на телефон.
8. Получение ZIP на `info@riklab.ru`.
9. Проверка темы письма: объект, вид ТО и дата.
10. Проверка логотипа, печати и подписи.

### Проверка сбоев

1. Свернуть Safari во время заполнения и вернуться.
2. Прервать интернет и повторить отправку.
3. Отправить комплект через мобильную сеть.
4. Одновременно сформировать отчёты с двух телефонов.
5. Проверить, что пользователи не видят черновики друг друга.
6. Проверить автоматическую очистку незавершённого комплекта.

### Нагрузочная проверка

Минимальный сценарий:

- 17 обязательных фотографий;
- несколько дополнительных фотографий;
- два одновременных пользователя;
- медленное мобильное соединение.

Необходимо отдельно измерять:

- время оптимизации на телефоне;
- время загрузки фотографий;
- время генерации PDF/DOCX;
- время SMTP-отправки;
- общий размер входящих фотографий, PDF и ZIP.

Это позволит отличить задержку мобильной сети от времени обработки российского
сервера.

## 12. Критерии приёмки

Внедрение считается завершённым, если:

- сервис открывается по российскому домену через HTTPS;
- на iPhone и Android черновик сохраняется после закрытия страницы;
- комплект стабильно формируется без `Load failed`;
- все четыре документа находятся в ZIP;
- ZIP скачивается на устройство и приходит на почту;
- акт не содержит отдельного приложения;
- логотип присутствует в акте и фотоотчёте;
- секреты отсутствуют в Git и журналах;
- временные файлы автоматически удаляются;
- два одновременных пользователя работают независимо.

## 13. Рекомендуемый порядок внедрения

1. Создать отдельную ветку для Node.js-адаптации.
2. Реализовать файловое хранилище и SMTP без изменения интерфейса сайта.
3. Поднять тестовый российский сервер и отдельный поддомен.
4. Провести тесты с реальными телефонами и мобильной сетью.
5. Сравнить размеры файлов и времена каждого этапа.
6. Провести пилот с двумя-тремя инженерами.
7. Сменить production-пароли.
8. Переключить основной домен только после успешного пилота.

## 14. Развитие после пилота

База данных понадобится, если потребуется:

- отдельная учётная запись для каждого инженера;
- история всех ТО;
- поиск по объекту, дате и оборудованию;
- статусы «черновик», «отправлен», «принят»;
- повторная отправка документов;
- централизованное редактирование справочника объектов;
- журнал действий пользователей.

Для первого переноса на российский сервер эти функции можно не внедрять.
